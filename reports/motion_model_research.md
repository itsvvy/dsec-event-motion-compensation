# Motion Model Research: Block Translation, Local Affine, and Homography

Status: historical pre-implementation design note. The three models have since
been implemented and validated on `main`; local affine is the current default,
and local homography is retained as a neutral optional result.

Baseline: `baseline-v0.1.0` (`30ae2bb`), the validated DSEC
constant-translation experiment.

## Executive decision

The recommended implementation order is:

1. block-wise translation;
2. local affine;
3. homography on selected planar regions.

This order is deliberate:

- block translation extends the already validated optimizer and is the cheapest
  way to address the observed left-side failure case;
- affine adds rotation, scale, and shear with six parameters per model;
- homography adds perspective but assumes a plane, so it should be evaluated
  per region rather than applied blindly to the full driving frame.

The implementation sequence followed this order. Each experiment used an
independent branch from stable `main` and was merged only after synthetic and
DSEC validation.

Current outcomes:

- B: mean median EPE `1.76 px`;
- BA: mean median EPE `1.52 px`, sub-2-px coverage `63.7%`;
- BH: mean median EPE `1.52 px`, sub-2-px coverage `62.8%`.

BA is the default. The actual BH implementation estimates local homographies
directly with ECC initialized by B; it does not use the proposed DLT/RANSAC
feature pipeline.

## Evidence from the baseline

The constant-translation baseline estimated local displacement by maximizing
the variance of the polarity-weighted event image. On the deliberately
multi-motion left patch, variance increased by 2.59-9.66x while endpoint error
against DSEC flow was 5.48-11.85 px. A sharper event image is therefore not
sufficient evidence of correct motion compensation.

This matches the known limitation of contrast maximization: it assumes one
motion model for all events being accumulated. Independently moving objects,
parallax, and rotation require either segmentation or a richer local model.

## Common implementation contract

All three models should use the same pipeline and expose the same interface.
This keeps comparisons meaningful and allows later models to be deployed on
RK3588 without changing the data or evaluation path.

```python
class MotionModel:
    def estimate(self, event_slices, mask, initial_parameters=None):
        """Return model parameters, confidence, and diagnostics."""

    def warp_events(self, x, y, normalized_time, parameters):
        """Return event positions at the reference time."""

    def warp_slice(self, event_image, normalized_time, parameters):
        """Apply the equivalent image warp for fast evaluation."""
```

Shared conventions:

- the event window is half-open and normalized to `tau in [0, 1)`;
- the reference image is generated at `tau=0.5`;
- an estimated endpoint parameter describes displacement from `t0` to `t1`;
- all models return confidence and a validity mask;
- low-confidence regions fall back to a coarser or safer model;
- invalid warp coverage is excluded rather than treated as black pixels.

## 1. Block-wise translation

### Model

Partition the image into overlapping tiles. Tile `(i,j)` receives a separate
endpoint translation:

```text
x_ref = x - vx_ij * (tau - 0.5)
y_ref = y - vy_ij * (tau - 0.5)
```

A dense displacement field is later reconstructed from the tile centers with
bilinear interpolation:

```text
dx(x,y) = interp(center_x_ij, center_y_ij, vx_ij, x, y)
dy(x,y) = interp(center_x_ij, center_y_ij, vy_ij, x, y)
```

### Recommended implementation

1. Use overlapping tiles, for example `96 x 96` pixels with a 48 px stride.
2. Build the same signed temporal event slices used by the baseline.
3. Use phase correlation between early/mid/late event images for a fast initial
   translation. Reject tiles with insufficient event support or a weak phase
   correlation peak.
4. Refine each reliable tile with the existing contrast objective over a small
   window, for example +/- 2 px at 1 px stride.
5. Compute confidence from event count, correlation peak, contrast gain, and
   agreement with neighboring tiles.
6. Replace low-confidence vectors with a robust median of neighboring vectors.
7. Warp all events with the interpolated `dx`, `dy` field.

Phase correlation gives fast sub-pixel initialization through a Fourier-domain
cross-power spectrum. The contrast refinement remains necessary because event
images are sparse, polarity-dependent, and not always generated by one motion.

### Advantages

- smallest implementation delta from the current baseline;
- deterministic, train-free, and easy to test on CPU;
- naturally handles independent motion at a coarse spatial scale;
- fast enough to remain a plausible RK3588 baseline.

### Risks

- piecewise-constant boundaries can create seams;
- interpolating opposite vectors across a moving-object boundary blurs the
  object edge;
- repetitive texture can produce false phase-correlation peaks;
- small tiles may contain too few events.

Mitigations are overlap, confidence-weighted neighbor regularization, and a
fallback to the global translation. Object-aware segmentation can be added
later, but is outside the first block-translation experiment.

## 2. Local affine

### Model

An affine transform adds rotation, non-uniform scale, and shear:

```text
x_ref = a*x + b*y + c
y_ref = d*x + e*y + f
```

The six parameters are collected as:

```text
theta = [a, b, c, d, e, f]
```

For a time-varying model, the transform assigned to the midpoint is the
identity, or the per-slice transform is estimated directly relative to the
reference slice. Direct per-slice estimation avoids assuming that affine
matrix coefficients vary linearly with time.

### Recommended implementation

1. Use block translations from the preceding model as initialization.
2. Fit an initial affine transform with RANSAC from reliable block centers and
   displacement vectors.
3. Optionally refine between two event images with
   `cv2.findTransformECC(..., cv2.MOTION_AFFINE, ...)`, using an event-density
   mask and a Gaussian-smoothed absolute-polarity image.
4. Refine the result with the contrast objective using a bounded local
   optimizer such as Powell or a small differentiable warping pass.
5. Reject transforms with low overlap, excessive scale/shear, mirrored
   orientation, or poor flow agreement.

Two levels are useful:

- one global affine for low-parallax and predominantly rotational motion;
- several local affine models over image sectors for mixed motion.

For local affine models, blend decomposed translation and linear terms rather
than averaging raw matrices without constraints.

### Advantages

- handles rotation and scale, which translation cannot;
- six parameters are much cheaper than dense optical flow;
- initializing from block translations avoids a cold nonlinear search;
- a fixed affine matrix is inexpensive to apply on RK3588.

### Risks

- nonlinear contrast optimization is sensitive to initialization;
- affine cannot represent perspective or depth-dependent parallax;
- smooth parameter interpolation may be physically inconsistent across a
  long time window;
- independently moving objects still require segmentation.

## 3. Homography

### Model

A planar projective transform has eight degrees of freedom:

```text
[x_ref, y_ref, 1]^T ~ H(t) [x, y, 1]^T
```

with the normalization `H[2,2] = 1`. A homography is physically appropriate for
points on one plane under camera motion. It is not a general model for a whole
driving scene containing road, sky, buildings, and independently moving cars.

### Recommended implementation

1. Define the target plane or region first. Candidate DSEC regions include the
   road surface, a building facade, or a manually selected planar patch.
2. Obtain point correspondences using one of:
   - feature detection and matching on dense event/time-surface images;
   - sparse KLT tracks between event images;
   - dense event optical flow, followed by sampling valid correspondences.
3. Normalize coordinates before DLT, then estimate `H` with RANSAC or MAGSAC.
   Require enough spatial support and reject degenerate layouts.
4. Score the result using inlier ratio, condition number, warped-area overlap,
   and event-image contrast.
5. Optionally refine `H` by direct contrast maximization after the robust
   feature/flow initialization.
6. If the region contains multiple planes or independent motion, estimate
   multiple homographies and assign events to the best model.

The final direct contrast refinement needs constraints:

- fix the scale ambiguity `H[2,2] = 1`;
- prevent triangle flips and self-intersection;
- penalize excessive area change;
- require minimum overlap after warping;
- cap parameter movement relative to the robust initial estimate.

### Advantages

- models perspective effect that affine cannot;
- natural fit for a ground plane or planar facade;
- robust DLT/RANSAC tools are mature and deterministic;
- a fixed homography is inexpensive to apply once estimated.

### Risks

- a global homography is physically wrong for mixed-depth scenes;
- event images can be too sparse for stable feature matching;
- robust estimation may select the largest plane while discarding the object
  of interest;
- direct contrast optimization has local minima and degenerate-warp failure
  modes;
- estimating multiple homographies is substantially more complex.

Homography should therefore graduate to a regional or multi-model experiment,
not replace the translation baseline on the whole frame.

## Recommended experiment branches

Branches should be created from stable `main` and retained after merge.

| branch | scope | first acceptance gate |
|---|---|---|
| `exp/blockwise-translation` | overlapping tiles, phase correlation, contrast refinement | improve left-patch flow error without regressing the two good patches |
| `exp/local-affine` | initial affine from block vectors, ECC/contrast refinement | lower median EPE than block translation on rotation-rich windows |
| `exp/homography` | RANSAC/DLT on one selected plane | beat affine inside the chosen plane with sufficient inlier/overlap support |

This common interface was a design proposal rather than the final code shape.
The implemented modules share data, event-image, block-field, and evaluation
utilities. Every model includes synthetic known-transform tests, and B/BA/BH
use the same three dense DSEC windows.

## Evaluation design

Primary correctness metric:

```text
EPE(x) = || (W_theta(x, t_i) - x) - flow_gt(x) ||_2
```

The constant baseline reports a per-patch median flow. The subsequent B/BA/BH
experiments evaluate at every valid DSEC flow pixel and report:

- median and mean EPE;
- fraction under 1, 2, and 3 px;
- direction error;
- per-region and per-flow-window results;
- transform validity/overlap and fraction of events warped out.

Image metrics remain secondary:

- event-image variance;
- gradient energy;
- Laplacian energy;
- residual polarity cancellation or alignment score.

Metrics must be compared to the same baseline commit, DSEC sequence, flow
timestamps, and window length. Results must include the pathological
multi-motion patch rather than selecting only successful patches.

## Compute and RK3588 implications

Estimated relative cost for a 640 x 480 event window:

| model | parameter search | per-event warp | deployment risk |
|---|---:|---:|---:|
| global translation | lowest | 4 arithmetic ops | lowest |
| block translation | low | interpolated translation | low |
| local affine | medium | 6-parameter affine | medium |
| homography | high | projective divide | medium |
| multi-homography | highest | model selection + divide | high |

Estimation cost, not per-event warp cost, is the main embedded concern. The
current Python/SciPy optimization is suitable for feasibility experiments but
not a final RK3588 implementation. A deployable version should:

- estimate models at a fixed cadence on downsampled event images;
- reuse the previous transform as initialization;
- use fixed-size tiles and bounded iterations;
- vectorize event warping;
- avoid Python object allocation in the frame loop;
- export the selected preprocessing path to C++ and benchmark on RK3588.

## Git and experiment-stage policy

- `main` is the only integration branch and must always pass the synthetic
  test, Python compile check, and the committed DSEC replay.
- Experiment branches are created from the current stable `main`.
- Algorithm changes reach `main` only through a pull request whose test and
  DSEC results are committed or linked.
- PRs use merge commits so the experiment history is preserved.
- Pushed commits and branches are never force-rewritten or deleted.
- Accepted experiments receive annotated stage tags, for example
  `experiment-v0.2-blockwise`, after merge.
- Raw DSEC archives stay outside Git; only configuration, checksums, compact
  metrics, and selected figures are committed.
